## 1. Контекст і проблема

Стаття показала, що plan-then-execute оркестратор набагато краще маршрутизує задачі між адаптерами, ніж ReAct tool-calling: plan F1 0.896 проти 0.365, coverage 0.867 проти 0.263, order score 0.804 проти 0.263. Водночас якість відповідей на рівні окремих кроків низька для обох систем. Причина не в оркестраторі, а в самих адаптерах:

- **Публічні адаптери не збігаються з бенчмарком.** Legal-адаптер навчений на LEDGAR (класифікація), а тестується на CUAD (span extraction). SQL exact match дорівнює 0.000.
- **Низькі показники multi-step:** task completion 0/20, error propagation 0.975. Один слабкий крок тягне вниз увесь ланцюжок.
- **Base models зникають з провайдерів:** Qwen2.5-7B у Tinker немає, а Llama-3.1-8B знята з підтримки.

Головна теза статті: якість залежить від ваг адаптерів, а не від рівня оркестрації. Цей проєкт перевіряє її експериментально. Ми тренуємо власні адаптери на даних, що збігаються з форматом задач, не змінюємо оркестратор і вимірюємо приріст якості.

## 2. Цілі

**G1.** Натренувати власні LoRA-адаптери для доменів SQL, legal і medical, які суттєво перевершують базову модель без адаптера на наших бенчмарках.

**G2.** Підняти метрики multi-step: step accuracy і task completion, знизити error propagation. Plan F1 при цьому не повинен погіршитися.

**G3.** Отримати чисте порівняння «публічні адаптери → власні адаптери» на незмінному оркестраторі. Це центральний результат для магістерської роботи та журнальної версії статті.

**G4 (stretch).** Натренувати LoRA для планера через RL з нагородою plan F1 + order score.

### Non-goals

- Зміни в архітектурі оркестратора чи контролера, крім конфігурації.
- Full fine-tuning базової моделі.
- Тренування на тестових задачах бенчмарку в будь-якій формі.
- Production-деплой і multi-GPU.

## 3. Метрики успіху

### 3.1 Базові лінії

### 3.2 Цільові показники

Перекалібровано після вимірювання B0 (етап E1, 2026-09-20; повні числа й контекст — `docs/results.md`, розділ "B0 — Qwen3-8B Passthrough Baseline").

| Метрика | Ціль | Мінімально прийнятно | B0 (виміряно) |
|---|---|---|---|
| SQL normalised EM | ≥ 0.40 | ≥ 0.15 (B0 + 0.15) | 0.000 |
| Legal token-F1 | ≥ 0.40 | ≥ 0.359 (B0 + 0.15) | 0.209 |
| Medical ROUGE-L | ≥ 0.30 | ≥ 0.237 (B0 + 0.10) | 0.137 |
| Single-domain pass rate (усі домени) | ≥ 35% | > 13.3% (B0; було > 12.5% B-old) | 13.3% |
| Multi-step step accuracy | ≥ 2× від B-old | > B-old | **не виміряно для B0** — `benchmarks/run.py` наразі не рахує цю метрику, див. нижче |
| Multi-step task completion | ≥ 5/20 | ≥ 2/20 | **не виміряно для B0** — той самий пробіл |
| Error propagation rate | ≤ 0.70 | < 0.975 | **не виміряно для B0** — той самий пробіл |
| Plan F1 | ≥ 0.85 | не нижче B-old − 0.05 (0.829) | **0.993 — вже перевищує ціль без жодного адаптера** |
| Латентність на запит (single-domain) | ≤ 1.2× B0 | ≤ 1.5× B0 | B0 = 6.0с у середньому (sql/code ~15с через відсутність "без пояснень" у промпті, решта ~1-2.5с) |

**Відкритий пробіл:** `avg_coverage`, `avg_step_accuracy`, `task_completion_rate`, `avg_error_propagation_rate` не рахуються поточною версією `benchmarks/run.py`/`multistep_metrics.py` — ці метрики з R2 (Qwen2.5-7B) звіту або зі старішої версії скрипта, або з ручного аналізу. Потрібно або доробити `multistep_metrics.py`, або вручну пройтись по сирих даних 50 задач з B0-прогону, перш ніж ці три рядки можна перекалібрувати. Позначено як TODO для E4, не вигадано наосліп.

**Несподіваний висновок з B0:** голий Qwen3-8B (без жодного оркестраторного адаптера) вже перевершує ціль по Plan F1 (0.993 проти цілі 0.85) і б'є B-old по кожній виміряній метриці планування. Це означає що вузьке місце для E3 — якість single-domain виводу (13.3% pass rate), не структура плану.

**Критерій успіху проєкту:** кожен власний адаптер статистично значуще перевершує B0 на своєму домені (paired bootstrap, p < 0.05) і не погіршує plan F1.

## 5. Функціональні вимоги

### 5.1 Дані

- **FR-D1.** Для кожного адаптера є тренувальний датасет у JSONL chat-форматі: `{"messages": [system, user, assistant]}`.
- **FR-D2.** System prompt у тренувальних даних дослівно збігається з `system_prompt` адаптера в `adapters.yaml`.
- **FR-D3.** Формат user/assistant збігається з форматом задач бенчмарку: та сама структура промпту й той самий формат відповіді, який очікує скорер.
- **FR-D4.** Кожен датасет пройшов перевірку на перетин із 120 single-domain і 20 multi-step задачами (див. 5.2). Перетин дорівнює нулю.
- **FR-D5.** Для кожного адаптера відкладено validation-спліт (~200 прикладів), який не перетинається ні з train, ні з бенчмарком.
- **FR-D6.** Для кожного джерела задокументовано: назву датасету на HF, ревізію (commit hash), ліцензію, спліт, кількість прикладів до та після фільтрації.
- **FR-D7.** Датасети версіонуються (приватний HF dataset repo або DVC), щоб експеримент можна було відтворити.

### 5.2 Пошук і відбір даних на HuggingFace

**Як шукати:**

1. **Веб-пошук на hf.co/datasets.** Фільтри: Tasks (Text2Text Generation, Question Answering, Summarization), Languages → English, License, Size. Сортування за Most downloads або Trending.
2. **Програмний пошук:**

   ```python
   from huggingface_hub import HfApi
   api = HfApi()
   for d in api.list_datasets(search="text-to-sql", sort="downloads", limit=20):
       print(d.id, d.downloads)
   ```

3. **Через статті.** На Papers with Code чи в самій статті бенчмарку часто є посилання на офіційний HF-репозиторій датасету.
4. **Dataset Viewer.** Перед завантаженням подивися реальні приклади в браузері й переконайся, що формат придатний.

**Чекліст відбору для кожного кандидата:**

- [ ] Є dataset card з описом походження даних.
- [ ] Ліцензія дозволяє дослідницьке використання й похідні моделі. Записати її.
- [ ] Є окремий train-спліт. Беремо тільки train.
- [ ] Формат задачі збігається з бенчмарком: той самий тип входу та виходу, а не просто «той самий домен».
- [ ] Якість: вибірково переглянути 50 прикладів, немає сміття чи обрізаних відповідей.
- [ ] Датасет не є джерелом наших тестових задач. Якщо є, взяти інший спліт і перевірити перетин.
- [ ] Датасет не згенерований іншою LLM без позначки. Якщо згенерований, зафіксувати це.

**Кандидати для старту.** Назви перевірити на HF перед використанням.

| Домен | Кандидати | Навіщо |
|---|---|---|
| SQL | `b-mc2/sql-create-context`, `xlangai/spider` (train) | Схема + питання → SQL, як у бенчмарку |
| Legal | `theatticusproject/cuad-qa` (train) | Той самий формат span extraction, що в бенчмарку |
| Medical | train-спліт джерела наших medical-задач; `qiaojin/PubMedQA`, `keivalya/MedQuad-MedicalQnADataset` | Відповіді з еталоном для ROUGE-L |
| Summarizer | `EdinburghNLP/xsum`, `abisee/cnn_dailymail` | Одне речення (xsum) ближче до наших задач |
| Grammar | `grammarly/coedit` (GEC-частина) | JFLEG має тільки dev/test, тож тренувати на ньому не можна |
| Code (RL) | train-задачі з тестами, наприклад MBPP train | HumanEval — наш тест, його не чіпаємо |

**Перевірка на перетин із бенчмарком (обов'язково):**

- Точний збіг після нормалізації (lowercase, прибрані пробіли й пунктуація).
- Near-duplicate: 13-gram overlap або MinHash (Jaccard ≥ 0.8) між кожним тренувальним прикладом і кожною тестовою задачею.
- Для SQL окремо: збіг пари «схема + питання».
- Результат перевірки зберігається як артефакт (`contamination_report_<domain>.json`).

Пошук даних на HuggingFace.

Де шукати. На hf.co/datasets фільтруй за Task, Language і License і сортуй за кількістю завантажень. Те саме можна робити з коду через HfApi().list_datasets(search="text-to-sql", sort="downloads").
Перед завантаженням. Переглянь приклади в Dataset Viewer і прочитай dataset card: звідки дані, яка ліцензія, чи є окремий train-спліт.
Головний критерій. Формат задачі має збігатися з вашим бенчмарком, а не лише домен. Наприклад, для legal потрібен CUAD-подібний span extraction, а не класифікація.
Кандидати для старту: b-mc2/sql-create-context, theatticusproject/cuad-qa, grammarly/coedit, EdinburghNLP/xsum.
Перевірка на перетин. Кожен датасет обов'язково перевір на перетин із вашими 120 + 20 задачами: точний збіг і MinHash / 13-gram.

### 5.3 Тренування (SFT)

- **FR-T1.** Базова модель `Qwen/Qwen3-8B`. Thinking вимкнено через відповідний renderer.
- **FR-T2.** LoRA rank 32. Це дорівнює поточним адаптерам і вкладається в `--max-lora-rank`.
- **FR-T3.** Learning rate з `hyperparam_utils.get_lr(model)` як відправна точка. Sweep ×{0.5, 1, 2} на P0-адаптерах.
- **FR-T4.** 1–3 епохи. Early stopping за validation-метрикою домену, а не лише за loss.
- **FR-T5.** Чекпоінти кожні N кроків. Фінальний чекпоінт обирається за validation-метрикою.
- **FR-T6.** Логи (loss, validation-метрики, конфіг, ревізія даних) зберігаються для кожного запуску.
- **FR-T7.** Seed фіксований. Для P0-адаптерів фінальний конфіг прогнати з 3 seeds, щоб отримати variance для статті. Це закриває limitation «single runs without variance».

### 5.4 Тренування (RL) — P1/P2

- **FR-R1.** SQL: нагорода 1, якщо результат виконання згенерованого SQL на тестовій БД збігається з результатом еталона, інакше 0. Бонус за валідний синтаксис. Стартова точка — SFT-адаптер.
- **FR-R2.** Code: нагорода — частка пройдених unit-тестів у sandbox. Відштовхуємося від рецепту Code RL у cookbook.
- **FR-R3.** Planner: нагорода = 0.5·plan F1 + 0.3·order score + 0.2·(валідний JSON-план). Потрібен тренувальний набір із 300–500 синтетичних multi-step задач з oracle-послідовностями, що не перетинається з 20 тестовими.
- **FR-R4.** Контроль reward hacking: вибірковий ручний перегляд 30 rollouts на кожному чекпоінті.

### 5.5 Експорт і деплой

- **FR-E1.** Чекпоінт завантажується через `weights.download` і конвертується в PEFT через `weights.build_lora_adapter`.
- **FR-E2.** `adapter_config.json` проходить валідацію: `peft_type: LORA`, rank ≤ `--max-lora-rank`, `target_modules` лише з attention/MLP (q/k/v/o_proj, gate/up/down_proj). Скрипт валідації з `serving.md` стає частиною пайплайна.
- **FR-E3.** Адаптер публікується в приватний HF-репозиторій з model card: дані, гіперпараметри, метрики, ліцензія.
- **FR-E4.** Адаптер додається в `adapters.yaml` з тим самим `system_prompt`, що й у тренувальних даних.
- **FR-E5.** vLLM оновлено до версії з підтримкою Qwen3. Smoke test: завантаження адаптера й одна інференс-відповідь через контролер.

### 5.6 Оцінювання

- **FR-V1.** Single-domain бенчмарк (120 задач) для B0, OURS і B-AM з тими самими скорерами й порогами.
- **FR-V2.** Multi-step бенчмарк (20 задач) для OURS і B-AM: plan F1, coverage, order score, step accuracy, task completion, error propagation, латентність.
- **FR-V3.** Ablation: OURS зі старими публічними адаптерами, де вони сумісні з Qwen3-8B. Якщо несумісні, використовуємо B0 як «без адаптерів».
- **FR-V4.** Статистика: paired bootstrap (10 000 ресемплів) для різниць між конфігураціями, 95% CI у таблицях.
- **FR-V5.** Усі прогони зберігаються як сирі JSON (кожна відповідь, оцінка, латентність), щоб таблиці можна було перерахувати.

## 6. Нефункціональні вимоги

- **NFR-1. Відтворюваність.** Один скрипт на домен: дані → тренування → експорт → оцінка. Конфіги в git.
- **NFR-2. Бюджет.** Загальні витрати на Tinker ≤ $100 (див. розділ 9).
- **NFR-3. Незалежність від провайдера.** Tinker знімає моделі з підтримки, тому всі фінальні адаптери експортуються й зберігаються на HF одразу після тренування. Серверний інференс відбувається на нашому vLLM і від Tinker не залежить.
- **NFR-4. Безпека секретів.** `TINKER_API_KEY` і `HF_TOKEN` лише в `.env`, не в git.
- **NFR-5. Ліцензії.** Кожен датасет і адаптер має записану ліцензію. Нічого з некомерційною ліцензією не використовується без позначки.

## 9. Бюджет

Оцінка за тарифом Qwen3-8B (~$0.44 за 1M train-токенів). Ціни перевірити на сторінці Models & Pricing перед стартом.

| Стаття | Розрахунок | Оцінка |
|---|---|---|
